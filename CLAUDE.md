# Bastion — правила работы с Claude

## Источник истины

Всё, что строим — по **PROJECT-SPEC.md**. Перед любым решением (структура, стек, модель) сверяйся с ним.

## Главное правило: один этап за раз

Этапы из раздела 5 PROJECT-SPEC.md — строго по порядку:

1. Каркас (solution, docker-compose, CI, healthcheck, Angular shell)
2. Домен + запасы (SupplyItem, CRUD, страница инвентаря)
3. Целевые уровни + ReadinessScore (индекс, дашборд, gap analysis, список докупок)
4. Оборудование + ТО (Equipment, MaintenanceTask, вклад в индекс)
5. Фоновые задачи + уведомления (Quartz, email, MailHog)
6. Полировка (сценарии, seed-данные, README, интеграционные тесты)

**Не начинай следующий этап**, пока текущий не компилируется, не проходит тесты и не работает end-to-end.

## После каждого этапа — объяснение

По завершении каждого этапа кратко пиши:
- **Что сделано** — конкретные файлы / компоненты
- **Почему так** — ключевые архитектурные решения и их обоснование
- **Что проверено** — как убедились, что этап работает

## Архитектурные ограничения

- Доменная логика — только в `Bastion.Domain`, без зависимостей на инфраструктуру
- `ReadinessScore` — чистая функция, без I/O, 100% покрытие тестами
- EF Core без raw SQL; только параметризованный, если всё же нужен
- Никаких секретов в репозитории: строки подключения, JWT-ключи — через env / user-secrets
- Naming и комментарии в коде — на английском; тексты UI — в константах, не хардкод в шаблонах

## Что НЕ делать

- Не добавлять фичи вне MVP (раздел 2 «Non-Goals»)
- Не добавлять абстракции «на будущее» (generic-репозитории ради паттерна и т.п.)
- Идеи вне MVP → фиксируй в `BACKLOG.md`, не в код
