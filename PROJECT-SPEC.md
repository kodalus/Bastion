# Проект «Bastion» — система готовности домохозяйства

> Промпт для Claude Code. Рабочее название проекта — Bastion (можно поменять).

## 1. Цель проекта

**Что это:** веб-приложение для управления домашними запасами и готовностью домохозяйства к чрезвычайным ситуациям — «мини-CMMS для дома» с преппер-уклоном. Учёт запасов (еда, вода, медикаменты, снаряжение) со сроками годности, целевые уровни запасов на семью, обслуживание оборудования по расписанию и общий «индекс готовности» дома.

**Зачем (два уровня):**
1. **Продукт:** реальный инструмент, которым автор будет пользоваться сам для своей семьи (4 человека).
2. **Портфолио:** демонстрация того, что senior .NET-разработчик с 13-летним опытом в desktop/WPF и промышленных системах (MES, CMMS, APS) владеет современным веб-стеком. Проект должен выглядеть как настоящий продукт, а не туториал: задеплоен, с тестами, CI, Docker и качественным README.

**Ключевая идея домена:** ротация запасов по срокам годности — это тот же паттерн, что плановое ТО оборудования в CMMS. Проект сознательно построен на этой аналогии, и доменная модель должна это отражать.

## 2. Границы (Non-Goals для v1)

Явно НЕ входит в MVP (не строить, но не блокировать архитектурно):
- Мобильное приложение и офлайн-режим
- Сканирование штрих-кодов
- Мультитенантность / регистрация посторонних пользователей (v1 — одно домохозяйство, простая аутентификация)
- Карты эвакуации, геолокация
- Интеграции с магазинами / автозаказ
- Локализация (v1 — интерфейс сначала на польском, в будущем - на английском; строки не хардкодить, чтобы локализация была возможна позже)

## 3. Пользовательские сценарии (MVP)

1. Как член семьи, я хочу добавить запас (например, «вода 5 л × 12») с категорией, местом хранения и сроком годности, чтобы система знала, что у нас есть.
2. Как член семьи, я хочу задать целевые уровни («14 дней воды на 4 человек», «запас лекарств X»), чтобы видеть, чего не хватает.
3. Как член семьи, я хочу видеть дашборд с общим индексом готовности (0–100%) и разбивкой по категориям, чтобы одним взглядом оценить состояние.
4. Как член семьи, я хочу получать уведомления (email) о запасах, у которых скоро истекает срок, чтобы использовать их по правилу FIFO и докупить новые.
5. Как член семьи, я хочу вести список оборудования (генератор, фильтры, аптечка, огнетушитель) с рекуррентными задачами обслуживания, чтобы ничего не просрочить.
6. Как член семьи, я хочу чек-листы на сценарии (отключение электричества, эвакуация), чтобы в стрессовой ситуации не думать.
7. Как член семьи, я хочу, чтобы система предлагала готовые нормы запасов (вода л/чел/день, калорийность еды, базовая аптечка) на основе общедоступных рекомендаций гражданской обороны, с возможностью их редактировать, чтобы не выдумывать цифры самостоятельно.
8. Как член семьи, я хочу видеть список докупок: чего не хватает до целевых уровней, в каком приоритете и сколько это ориентировочно стоит (по позициям и суммарно), чтобы планировать бюджет и закрывать самое важное первым.

## 4. Архитектура

### Стек
- **Backend:** ASP.NET Core 8 Web API, C# 12
- **Архитектурный стиль:** Clean Architecture + DDD-light (богатая доменная модель там, где есть логика; без оверинжиниринга)
- **ORM / БД:** EF Core 8 + PostgreSQL
- **Фоновые задачи:** Quartz.NET (скан сроков годности, генерация задач ТО, отправка уведомлений)
- **Email:** MailKit; в dev-окружении — MailHog в docker-compose
- **Frontend:** Angular 17+ (standalone components, signals), Angular Material или Tailwind — на выбор, главное аккуратный дашборд с графиками (ngx-charts или Chart.js)
- **Контейнеризация:** Dockerfile для api и frontend, docker-compose (api + frontend + postgres + mailhog); весь проект поднимается одной командой `docker compose up`
- **CI:** GitHub Actions — build, тесты, сборка docker-образов
- **Тесты:** xUnit (домен + application), интеграционные тесты API через Testcontainers (реальный PostgreSQL)

### Структура решения


### Доменная модель (ядро)

- **Household** — домохозяйство: название, список членов (Member: имя, возраст — влияет на нормы потребления).
- **StorageLocation** — место хранения (кладовка, подвал, машина, «тревожный чемодан»).
- **SupplyItem** — единица запаса: название, категория (Water, Food, Medical, Hygiene, Energy, Tools, Documents), количество + единица измерения, место хранения, срок годности (nullable), ориентировочная цена за единицу (nullable), дата добавления. Партии одного продукта с разными сроками — отдельные записи (FIFO).
- **TargetLevel** — целевой уровень по категории: норма на человека в день × целевой горизонт в днях (например, вода: 3 л/чел/день × 14 дней). Из Household считается требуемый объём. При первом запуске система заполняет редактируемые пресеты норм на основе общедоступных рекомендаций гражданской обороны (вода ~3 л/чел/день, еда ~2100–2500 ккал/чел/день, базовая аптечка, гигиена) — пользователь может их менять, пресеты хранятся как данные, не хардкод.
- **ShoppingListItem** — позиция списка докупок (вычисляется из gap analysis, редактируется пользователем): категория/позиция, дефицит до целевого уровня, приоритет (High/Medium/Low; вода, еда и медикаменты по умолчанию выше), оценочная стоимость закрытия дефицита (дефицит × средняя цена из данных пользователя или введённая вручную), суммарный бюджет списка. Отметка «куплено» создаёт соответствующий SupplyItem.
- **Equipment** — оборудование: название, категория, дата покупки.
- **MaintenanceTask** — рекуррентная задача обслуживания оборудования: описание, интервал (RRULE-подобная модель или простой интервал в днях), дата последнего выполнения, вычисляемая дата следующего. Прямая аналогия planned maintenance из CMMS.
- **Scenario + ChecklistItem** — сценарий ЧС и его чек-лист.
- **Notification** — исходящие уведомления (лог отправленных, чтобы не дублировать).

### Индекс готовности (ReadinessScore)
Доменный сервис, чистая функция без I/O (легко тестируется):
- По каждой категории: `score = min(100, доступный_объём_с_учётом_сроков / требуемый_объём × 100)`. Запасы с истёкшим сроком не считаются; запасы, истекающие в ближайшие N дней, считаются с понижающим весом.
- Отдельный компонент за оборудование: доля задач ТО, выполненных вовремя.
- Общий индекс — взвешенное среднее категорий (веса конфигурируемы, вода и еда весят больше).
- На дашборде: общая цифра + разбивка + список «что докупить» с приоритетами и оценочной стоимостью (gap analysis + бюджет закрытия дефицита).

### Фоновые задачи (Quartz.NET)
1. **ExpiryScanJob** (ежедневно): находит запасы, истекающие в ближайшие 30/7 дней, создаёт уведомления.
2. **MaintenanceDueJob** (ежедневно): проверяет просроченные и приближающиеся задачи ТО.
3. **NotificationDispatchJob**: отправляет накопленные уведомления email-ом (digest, не спам по одному).

### API (набросок)
REST, ресурсный стиль: `/api/supplies`, `/api/supplies/{id}`, `/api/targets`, `/api/equipment`, `/api/equipment/{id}/maintenance-tasks`, `/api/scenarios`, `/api/dashboard/readiness` (агрегат для главного экрана), `/api/locations`. Swagger/OpenAPI включён.

### Аутентификация
v1: простая cookie- или JWT-аутентификация с одним зарегистрированным домохозяйством (seed-пользователь). Без ролей. ASP.NET Core Identity не обязателен — можно минимально.

### Безопасность (сквозное требование, не отдельный этап)
Проект должен демонстрировать осознанный подход к безопасности — это часть портфольной ценности:
- **Никаких секретов в репозитории.** Строки подключения, JWT-ключи, SMTP-креды — только через переменные окружения / .NET user-secrets в dev; в репозитории лежит `.env.example` с плейсхолдерами. `.gitignore` исключает `.env`, `appsettings.*.local.json`.
- **Аутентификация:** JWT с коротким временем жизни + refresh token; пароли — только через ASP.NET Core PasswordHasher (Argon2/PBKDF2), никакого самопального хэширования.
- **Валидация входных данных** на границе API (FluentValidation или DataAnnotations), возврат ProblemDetails, без утечки stack trace наружу (глобальный exception handler).
- **EF Core без raw SQL** (защита от SQL-инъекций по умолчанию); если raw SQL понадобится — только параметризованный.
- **Rate limiting** на auth-эндпоинтах (встроенный ASP.NET Core RateLimiter).
- **HTTPS + security headers** (HSTS, X-Content-Type-Options, CSP для фронтенда), корректно настроенный CORS (белый список, не `*`).
- **Dependabot** включён в репозитории (обновления зависимостей), CI падает при уязвимых пакетах (`dotnet list package --vulnerable` в pipeline).
- В README — короткий раздел «Security considerations» с перечислением этих мер: рекрутёр должен увидеть это текстом, не раскапывая код.

## 5. Этапы работы (строго по порядку, каждый этап завершается работающим состоянием)

1. **Каркас:** solution по структуре выше, docker-compose с PostgreSQL, EF Core, первая миграция, healthcheck endpoint, CI на GitHub Actions (build + test). Пустой Angular-проект собирается и отдаётся.
2. **Домен + запасы:** SupplyItem, StorageLocation, категории; CRUD API + юнит-тесты домена; страница инвентаря в Angular (таблица, фильтры по категории/месту, сортировка по сроку годности).
3. **Целевые уровни + ReadinessScore:** TargetLevel, доменный сервис индекса с полным покрытием тестами, endpoint дашборда, экран дашборда с индексом и разбивкой. Пресеты норм (seed), gap analysis: список докупок с приоритетами и оценочной стоимостью.
4. **Оборудование + ТО:** Equipment, MaintenanceTask, рекуррентность, вклад в индекс.
5. **Фоновые задачи + уведомления:** Quartz jobs, email через MailHog в dev, лог уведомлений.
6. **Полировка:** сценарии/чек-листы, seed-данные (реалистичное демо-домохозяйство), README со скриншотами и инструкцией «одна команда — и всё работает», интеграционные тесты ключевых сценариев.

- [ ] README: описание, скриншоты, архитектурная схема, стек, инструкция запуска, фраза об источнике доменной экспертизы (опыт промышленных CMMS)
- [ ] Выполнены все пункты раздела «Безопасность»; в репозитории нет ни одного секрета (проверено, включая историю коммитов)
- [ ] Ни одного TODO/закомментированного мусора в main

## 7. Инструкции по стилю работы

- Работай поэтапно по разделу 5; не начинай следующий этап, пока текущий не компилируется, не проходит тесты и не работает end-to-end.
- Доменная логика — в Domain, без зависимостей на инфраструктуру. ReadinessScore обязан быть чистой тестируемой функцией.
- Не добавляй фичи вне MVP (раздел 2 и 3), даже если «просится». Идеи фиксируй в файле `BACKLOG.md`.
- Комментарии и naming в коде — на английском. Тексты UI — вынесены в константы/файлы, не размазаны по шаблонам.
- Простота важнее универсальности: никаких лишних абстракций «на будущее», generic-репозиториев ради репозиториев и т.п. Код должен читаться как код уверенного сеньора, а не как демонстрация паттернов.
